# tmem — память + KV-кэши в трансформерах

Промышленная переработка ноутбука `Transformer(1).ipynb` в пакет Python с
тестами и бенчмарком. Ноутбук исследовал идею **внешней ассоциативной памяти**
(`Memory` со слотами, косинусным ретривингом, TTL-вытеснением и слиянием
дубликатов), инжектируемой в слои T5/GPT-2/Qwen2 через хуки, и сравнивал
её с «полным контекстом» по токенам/латентности/качеству ответов.

Что добавлено сверх ноутбука: честное сравнение с **классическим KV-кэшем**
и **разреженным KV-кэшем** (sliding/StreamingLLM-стиль и topk/H2O-стиль) на
явном цикле декодирования, плюс сверка ответов с заранее заготовленными
вопросами (keyword-scoring), и итоговая **двухканальная память** (текстовый
RAG-банк + латентные K/V в attention), описанная в статье
`results/report/PAPER.md`.

## Как устроена двухканальная память (v4)

Финальная система (стратегия `v4_rag_kv`, в таблицах статьи — «Двухканальная
память») — это **замороженная Qwen3.5-4B без какого-либо обучения**, вокруг
которой работают два независимых канала памяти и короткий буфер последних
ходов. Прогон хода реализован в `tmem/dialogue.py::run_session`; точные
параметры стратегии заархивированы в `protocol.strategies` файла
`results/qwen35_comparison/qwen35-4b_battery100.json` (определения —
`tmem/corpus_run.py::main_strategies` и `tmem/stress.py::battery_strategies`).

Смысл разбиения на каналы: **текстовый канал** переносит дословные значения
фактов (числа, имена, коды) через промпт, а **латентный канал** даёт модели
дополнительное «состояние темы» напрямую в attention, минуя текст.

### Конвейер одного хода

1. **Эмбеддинг текущей реплики.** `semantic.embed_utterance` вычисляет
   $e(x)$ — среднее по позициям токенов **последнего** скрытого слоя той же
   модели (`hidden_states[-1]`, реплика обрезается до 128 токенов).
   Важно: это и есть **эмбеддинг запроса в RAG** — той же функцией
   эмбеддируются и реплики, которые кладутся в текстовый банк, и текущий
   вопрос, по которому из банка достаются заметки. Никакого отдельного
   эмбеддера нет.
2. **Retrieval заметок.** `RagBank.retrieve(query=e(x))` возвращает top-4
   текста по косинусной близости (формула (2) статьи). Текущая реплика на
   момент поиска ещё не в банке — банк пополняется после ответа (шаг 6).
3. **Сборка промпта.** `dialogue._prompt` + `models.ModelBundle.to_chat`:
   чат-шаблон + блок `Relevant notes:` (найденные заметки) + буфер последних
   ходов + `User: <текущая реплика>`. Буфер при `window=5` — это
   `history[-2*window:]`, причём каждый элемент `history` содержит **пару**
   `User: … Assistant: …`, то есть фактически удерживаются **10 последних
   ходов** — статья §2.2 после сверки (ноябрь 2026) исправлена на «десять»,
   код не менялся.
4. **Генерация.** Явный цикл декодирования `generate.decode_causal`
   (greedy, seed на ход, ≤32 новых токенов) с классическим неограниченным
   KV-кэшем — промпт короткий (максимальный кэш в батарее — 635 токенов),
   сжимать нечего.
5. **Латентный канал во время генерации.** Четыре средних full-attention
   слоя (у Qwen3.5-4B это слои 11, 15, 19, 23 из 32) обёрнуты в
   `kvinject.KVMemoryAttention`: на каждом forward отобранные векторы из
   латентного банка входят в attention как дополнительные ключи/значения
   (подробнее ниже).
6. **После ответа.** Пользовательская реплика добавляется в текстовый банк
   (`bank.add`; вопросы и собственные ответы модели не сохраняются).
   Эмбеддинг ответа вычисляется только для метрики tone. Латентный банк
   пополняется исключительно изнутри генерации — скрытыми состояниями тех
   же четырёх слоёв.

### Канал 1 — текстовый RAG-банк (`tmem/semantic.py::RagBank`)

* **Запись**: текст реплики + её эмбеддинг $e_j$ + номер хода. Ёмкость 256
  записей, при переполнении вытесняется старейшая.
* **Центрирование (v3)**. Банк ведёт бегущее среднее $c$ по всем принятым
  репликам (вопросы исключены). При записи сохраняется
  $u_j=(e_j-c)/\lVert e_j-c\rVert_2$, где $c$ — среднее **на момент записи**
  (первая реплика центрируется по $c=0$); позже старые записи не
  пересчитываются. Запрос центрируется текущим $c$. Смысл: сырые эмбеддинги
  одной модели анизотропны (взаимные косинусы ~0,95+), вычитание общей
  компоненты оставляет «сигнал» факта (формула (1) статьи; оговорки про
  фиксацию центрирования внесены в статью при сверке).
* **Ранжирование**: четыре ближайшие к запросу записи банка по косинусной
  близости; векторы нормированы, поэтому она сводится к скалярному
  произведению $u\cdot q$ (формула (2) статьи). В коде — одним матричным
  произведением `embeds @ probe` (строки матрицы банка на столбец запроса);
  транспонирование в записи $u^{\top}q$ — лишь матричное соглашение для
  векторов-столбцов.
* **Upsert**: при близости ≥ `rag_crit = 0.95` новая реплика **заменяет**
  найденную запись — обновление факта («кот переименован в Simba»)
  перезаписывает прежнюю версию, а не плодит запись-близнеца.
* RAG-контроль (`rag_text_only`) — то же самое, но `centered=False` (сырые
  нормированные эмбеддинги) и без латентного канала.

### Канал 2 — латентная память в attention (`tmem/memory.py` + `tmem/kvinject.py`)

Банк активаций — та самая `Memory` из ноутбука: 512 слотов × 2560 (fp32),
**общая для всех четырёх инструментированных слоёв** (`CorrectionLayer`
создаётся один раз и передаётся каждому слою).

* **Retrieval** (`Memory.get_relevant`): запрос — скрытые состояния текущего
  вызова слоя (все токены); близость слота = **максимум** косинусов по
  позициям токенов; берётся top-256 занятых слотов, обёртка оставляет top-32
  (`kv_slots`). Поиск выполняется **до** обновления банка текущими
  состояниями (`CorrectionLayer.forward`: retrieve → update).
* **Инъекция** (`KVMemoryAttention.__call__`): если $A$ — отобранные векторы,
  то

  $$K_m=R_K(W_KA),\qquad V_m=W_VA,\qquad \widetilde K=[K;K_m],\qquad \widetilde V=[V;V_m],$$

  где $W_K,W_V$ — проекции **текущего слоя**, а $R_K$ — нормировка ключей
  Qwen3.5 (QK-Norm; добавлена в формулу (4) статьи при сверке). RoPE к памяти
  **не применяется** (факт беспозиционен относительно потока реплик).
  Конкатенация делается **после** `past_key_values.update`, поэтому память не
  попадает в последовательный KV-кэш; аддитивная маска расширяется нулевыми
  столбцами (`_extend_mask`) — слоты памяти видны всем реальным токенам,
  причинность между токенами не меняется.
* **Update** (`Memory.update`), для каждого вектора $h$ текущих скрытых
  состояний:
  * близость к лучшему слоту ≥ `memory_crit = 0.95` → EMA-слияние
    $a\leftarrow 0{,}75\,a+0{,}25\,h$ (`merge_k = 0.25`; формула (3) статьи,
    $\lambda=0{,}75$), TTL слота поднимается до ≥5;
  * иначе близость ≤ `max_to_new = 0.4` **и** пройден гейт активности
    (`Memory.check`: сумма любого окна в 32 измерения > `window_crit = 0.5`)
    → вектор занимает свободный слот с TTL = 5;
  * иначе вектор отбрасывается («серая зона» 0.4…0.95 не хранит и не сливает).
* **TTL**: хит при retrieval даёт +2 (потолок 6); **каждый вызов** attention
  каждого из четырёх слоёв уменьшает TTL всех слотов на 1 и вытесняет слоты с
  TTL ≤ 0. Так как банк общий и вызывается из 4 слоёв, фактически за один шаг
  декодирования TTL тает на 4 — статья §2.4 после сверки описывает это явно.

### Метрики батареи (`tmem/stress.py::analyze_session`, `tmem/metrics.py`)

* **recall** (формула (6)) — среднее по 24 probes `keyword_score`: доля
  ожидаемых ключевых строк, найденных в ответе (без учёта регистра). В батарее
  у каждого probe ровно **одна** ключевая строка, поэтому оценка вырождается в
  индикатор 0/1 и «20 из 24 = 0,833» корректно.
* **stale** — доля **всех 24** ответов, содержащих прежнее (заменённое)
  значение; probes без stale-ключа дают 0.
* **tone** — `semantic.tone_alignment`: максимальный косинус эмбеддинга ответа
  с **нецентрированными** эмбеддингами реплик банка (общий для всех 107 ходов).
* **rep** (формула (7)) — `semantic.repetition_rate`: $1-U/G$ по словесным
  триграммам ответа.
* **attention-прокси** (формула (8)) — `generate.DecodeResult.total_cache_slots`:
  сумма средних длин KV-кэша по слоям (`compat.cache_mean_length`) после
  prefill и после каждого шага генерации, по всем ходам. У Qwen3.5 K/V хранят
  только 8 full-attention слоёв (линейные слои не дают K/V-тензоров), поэтому
  $L=8$ — как в статье.
* **экономия** (формула (9)) — `report_data.cost_rows`: прокси полного
  контекста / прокси метода.
* **латентность** — wall-time `decode_causal` (prefill + decoding); внешние
  embedding и retrieval в неё не входят (статья это оговаривает).

## Ноутбук → пакет: эволюция системы

То, что делалось в `Transformer(1).ipynb` (v1), и финальная система статьи
(v4) — разные стадии одного подхода:

| | Ноутбук (v1) | Финальная система (v4_rag_kv) |
|---|---|---|
| Банк активаций | `Memory`: 512 слотов, косинус-ретривинг (max по позициям), TTL +2/−1 (потолок 6, новый = 5) | та же `tmem/memory.py` (алгоритм 1-в-1, исправлен баг `__empty_slots`); банк **общий** для 4 слоёв |
| Слияние слотов | среднее `consume = (a+b)/2`, порог 0.8 | EMA $a\leftarrow0{,}75a+0{,}25h$, порог 0.95 |
| Гейт хранения | сумма окна 32 > 10 | сумма окна 32 > 0.5 |
| Инъекция в модель | аддитивно: `hidden += β·mean(relevant)` (GPT-2/Qwen2, cell 1), конкатенация в энкодер T5 (cell 2) | дополнительные **K/V в attention** четырёх средних слоёв (`kvinject.py`); аддитивный хук в v4 **не используется** |
| Текстовый канал | нет | `RagBank`: top-4 заметки в промпт, upsert 0.95, центрирование по бегущему среднему |
| Контекст диалога | срез последних 3–5 **сообщений** (`history[-3:]`, `history[-5:]`) | срез последних `2·window` **пар** User+Assistant (`window=5` → 10 пар) |

Промежуточные версии: **v2** — EMA-слияние + текстовый RAG-банк с upsert и
gist-ретривингом (`semantic.py`); **v3** — центрирование эмбеддингов банка
(борьба с анизотропией); **v4** — латентная память как K/V средних слоёв
(`kvinject.py`). В финальной батарее gist-ретривинг выключен
(`rag_lambda = 0`) — центрирование даёт тот же эффект «бесплатно».
v1 с аддитивным хуком остаётся в стратегиях `window_hybrid_memory` /
`v1_memory` и в тестах. Отдельная ветка экспериментов — обучаемые LoRA-reader'ы
для канала KV-памяти (`trainreader.py`), в статью не вошла.

## Запуск тестов

```bash
.venv/bin/python -m pytest -q                 # unit-тесты, CPU, офлайн
.venv/bin/python -m pytest -m integration -q  # реальный GPT-2 на CPU (нужна сеть)
.venv/bin/python -m pytest -m gpu -q          # ТОЛЬКО по согласованию, ROCm/CUDA
```

Маркеры `integration` и `gpu` исключены из прогона по умолчанию
(`pyproject.toml → addopts`).

### Что проверяют тесты

* **память**: хранение/гейт активности, слияние дубликатов, «серая зона»
  схожести, лимит ёмкости, TTL (+2 бонус за хит, −1 за запрос, вытеснение),
  консистентность Buchkeeping (регрессия бага ноутбука с `__empty_slots`),
  детерминизм, границы `count`;
* **хуки**: форма/маска конкатенации энкодера, сброс position_bias,
  аддитивный путь декодера (включая fp16), passthrough при пустой памяти,
  регистрация на реальных блоках GPT-2/T5;
* **KV-кэш**: эквивалентность классического кэша пересчёту без кэша
  (токен-в-токен!) — и на крошечных моделях, и на настоящем GPT-2;
  разреженный кэш с огромным бюджетом == классический; скользящее/топковое
  вытеснение держит бюджет, не ломает генерацию и экономит attention-работу;
* **диалоги**: все 6 стратегий на обеих архитектурах (causal и encoder-decoder),
  экономия токенов у window/hybrid, накопление памяти, скоринг probing-вопросов;
* **QA/метрики/CLI**: keyword-скоринг, корректность эталонов, прогон `answer_questions`.

## Примечания по железу

Видеокарта — **AMD Radeon RX 7900 XTX (Navi 31)**: NVIDIA/CUDA нет, PyTorch
нужен в ROCm-сборке (`pip install torch --index-url
https://download.pytorch.org/whl/rocm6.x`), устройство при этом называется
`cuda`. Текущий `.venv` содержит ROCm-сборку PyTorch 2.9.1; основная батарея
Qwen3.5-4B выполняется в bf16.

## Ограничения (задокументированы честно)

* буфер компактных систем — 10 последних ходов (5 пар User+Assistant при
  `window=5`): статья, таблица 2, рисунок 1 и отчёт приведены к этому в
  правке по итогам сверки (ноябрь 2026); числа батареи измерены именно с
  таким буфером;
* sparse-кэш для T5 чистит только decoder self-attention кэш; относительные
  позиции T5 корректны при `sliding` (окно остаётся связным), при `topk`
  возможны смещения bias;
* `topk`-важность — накопленная сумма внимания (H2O-подобная), attention
  включается через `eager`-реализацию;
* PyramidKV требует раздельные attention-маски для слоёв с разной длиной кэша;
  на GPT-2 с его общей маской политика явно отклоняется, на Qwen3.5 поддерживается;
* метрики качества — эвристики ноутбука (лексика), семантической оценки нет;
* `Memory.check` (гейт по сумме окна) унаследован из ноутбука как есть —
  он чувствителен к знаком активаций; порог вынесен в
  `Strategy.memory_window_crit`.

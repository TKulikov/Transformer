# План: полномасштабные тесты двухканальной памяти (multi-dialogue benchmark)

Статус: **утверждён заказчиком**; шаги 1–2 выполнены (код + тесты, GPU не
требовался), шаг 3 (пилот) ожидает освобождения GPU

## Цель

Устранить угрозы валидности, заявленные в статье (`results/report/PAPER.md`, раздел
«4 ОБСУЖДЕНИЕ»): один синтетический диалог, один прогон, все вопросы lag 21+,
нет абляций компонентов, латентность без warmup и повторов. На выходе —
статистически обоснованное сравнение двухканальной памяти с контролями на
корпусе диалогов, различающихся по **теме**, **«пользователю» (персоне)**,
**ситуации** и **длине**, с доверительными интервалами и значимостью различий.
Финал — обновлённая статья с многодиалоговой оценкой.

## Контекст (что прочитано перед планированием)

- `tmem/stress.py` — `Fact` (plant/question/paraphrase/update/stale_topic),
  `build_long_session`, `build_adversarial_session` (близнецы Oxidum/Oxidus),
  `build_battery_100` (16 фактов, 24 пробы, все в последней трети),
  `battery_strategies` — **уже содержит заготовки абляций**: `v1_memory`,
  `v2_rag_plain`, `v2_rag_gist`, `v3_rag_centroid`, `v4_kv_mid` (латентный
  канал без текста), `v4_rag_kv` (финальная система), плюс window-контроли.
- `tmem/dialogue.py` — флаги `Strategy`: `rag_centered`, `rag_crit` (upsert),
  `rag_k`, `memory_kv`, `kv_slots`, `window`; `run_session`.
- `tmem/cli.py` — `--battery100` (одна сессия), `--stress --sessions` (список
  сессий), `--strategies`, `--models`, `--out`.
- `scripts/report_data.py` — загрузчик ОДНОЙ серии JSON (`qwen35_comparison`).
- Статья: recall 0,833 против 1,000 (полный контекст), 0,750 (PyramidKV);
  латентность 1,34 с vs 1,84 с — всё на одном диалоге, одном прогоне.

## Решённое (ограничения, которые уважаем)

- Модель и железо те же: Qwen/Qwen3.5-4B bf16, AMD RX 7900 XTX (24 ГБ), ROCm.
- Все политики — в едином цикле декодирования `tmem` (сопоставимость).
- Детерминированная генерация (greedy); «повторы» нужны для латентности, а не
  для качества (при greedy seed не меняет текст ответа).
- Результаты — JSON на сессию + агрегат; всё воспроизводимо одной командой.
- Бюджет KV по умолчанию 128 слотов/слой (как в статье).
- **Батчевая модель исполнения (требование заказчика)**: минимальная единица
  прогона — один диалог × все стратегии («батч»). После каждого батча сняты
  результаты и обновлён промежуточный отчёт; пауза/остановка GPU-сессии
  допустимы в любой момент между батчами без потери данных. Детали — в
  разделе «Батчевая модель» ниже.

## Оси вариации (требование заказчика)

| Ось | Значения | Как реализуем |
|---|---|---|
| **Тема** | 6 доменов: работа/IT-проект, путешествие, здоровье, покупки/финансы, учёба, дом/хобби | пулы `Fact` + тематические filler-реплики на домен |
| **«Пользователь»** (персона) | 4 стиля: лаконичный; болтливый-эмоциональный; небрежный (опечатки, обрывы); формальный (канцелярит) | шаблоны plant/вопросов/filler-ов персоны, обёртка над фактами |
| **Ситуация** | 5 типов: baseline; обновления фактов (2–4); противоречия/близнецы (adversarial); дистраторы (семантически близкая болтовня не по фактам); мультифакт (2–3 факта в одной реплике) | генератор расстановки растений и filler-ов |
| **Длина / lag** | 40 / 100 / 200 ходов; пробы во ВСЕХ зонах lag: 1–5, 6–20, 21+, 50+ (не только в конце!) | `target_turns` + равномерная сетка `after_turn` |
| **Тип пробы** | direct; paraphrase; multi-hop (комбинация 2 фактов); temporal («какое значение было ДО обновления?»); unanswerable (факт не сажался → ждём отказа, меряем галлюцинации) | новые поля `Probe.kind`, расширение скоринга |

Итого базовый корпус: 6 тем × 4 персоны × 5 ситуаций = **120 диалогов**
(полный факториал не обязателен — см. латинский квадрат в шаге 3).

## Батчевая модель исполнения (пауза в любой момент)

**Батч = 1 диалог × все стратегии набора** (7 основных; для абляционной сетки —
свой набор). Это минимальная атомарная единица: прерывание внутри батча
теряет только текущий диалог (он перезапускается целиком), прерывание между
батчами не теряет ничего.

- **Сбалансированный порядок батчей.** Очередь формируется round-robin по
  осям (тема → персона → ситуация → длина), а не подряд по темам: любой
  префикс корпуса (первые 8, 16, 24… диалогов) примерно равномерно покрывает
  все темы/персоны/ситуации. Остановка «на середине» даёт несмещённые
  частичные результаты, которые уже можно публиковать как промежуточные.
- **Чекпоинты и resume.** Состояние прогона = набор JSON-файлов
  `results/corpus/<run_id>/<batch_id>/<strategy>.json` + манифест
  `manifest.jsonl` (batch_id, статус, wall-time, версии кода/модели).
  Завершённые батчи при повторном запуске пропускаются; частично записанный
  батч детектируется по манифесту и перезапускается. Внешней БД не нужно —
  файловая система и есть чекпоинт.
- **Промежуточный отчёт после каждого батча.** Раннер автоматически
  обновляет `results/corpus/<run_id>/INTERIM.md`: прогресс (N/48 батчей,
  wall-time, оценка остатка), сводная таблица recall по стратегиям с
  накопительными 95 % ДИ (бутстреп по завершённым диалогам), срезы по
  темам/персонам/lag — на текущих данных. Просмотр не требует ручного
  запуска агрегатора.
- **Режимы запуска раннера** (`python -m tmem.corpus_run …`):
  - `--batches N` — выполнить N батчей и остановиться (удержание GPU
    фиксированное, например вечерняя сессия на 2–3 часа);
  - `--all` — вся очередь, но Ctrl-C/остановка безопасны в любой момент;
  - `--only BATCH_ID…` — точечный перезапуск конкретных диалогов;
  - `--dry-run` — показать очередь, прогресс и оценку времени без GPU.
- **Честность латентности внутри батча сохраняется**: warmup + ≥5
  чередующихся повторов всех стратегий одного диалога (A,B,A,B,…), порядок
  стратегий ротируется между батчами.
- Планирование GPU-сессий: после пилота (шаг 3) будет известно wall-time
  батча для длин 100 и 200 ходов → `INTERIM.md` и `--dry-run` показывают,
  сколько батчей влезает в доступное окно (например, «4 батча ≈ 3 часа»).

**Порядок осей в очереди (пример):** T1P1S1L100 → T2P2S2L100 → T3P3S3L100 →
T4P4S4L100 → T5P1S2L100 → … → затем второй круг с L200. Первые ~12 батчей
уже покрывают все 6 тем и все 5 ситуаций.

## Шаги

### Шаг 1. Генератор корпуса — `tmem/corpus.py` *(новый модуль)*
- [x] Схема данных: `Topic` (пул фактов, filler-пул), `Persona` (стилевые
      шаблоны реплик и вопросов), `Scenario` (расстановка: updates /
      adversarial-twins / distractors / multi-fact), `CorpusSpec` (seed,
      target_turns, lag-зоны, число проб каждого типа).
- [x] Генератор `build_corpus_session(spec) -> DialogSession`: детерминированный
      по seed; пробы распределены по lag-зонам; каждый факт уникально
      идентифицируем (валидатор: ожидаемые ключевые строки не встречаются в
      чужих фактах и filler-ах данного диалога).
- [x] Расширение `Probe.kind` + скоринг в `tmem/qa.py`: multi-hop (все части
      ответа), temporal (ожидаемо СТАРОЕ значение), unanswerable (успех =
      отказ/«не знаю», ошибка = любая конкретная value-строка).
- [x] Экспорт/импорт spec-ов в JSON (диалог = данные, не код).
- **Проверка**: юнит-тесты — детерминизм (2 запуска одного seed → идентичный
  JSON), корректность lag-зон, валидатор уникальности ответов ловит
  специально испорченный spec.

### Шаг 2. CLI, раннер батчей и протокол измерений — `tmem/corpus_run.py` *(новый)*, `tmem/cli.py`, `tmem/dialogue.py`
- [x] Режим `--corpus SPEC.json` (или `--corpus-preset pilot|main|ablation`):
      grid сессий × стратегий, по одному JSON на сессию в структуре
      `results/corpus/<run_id>/<batch_id>/`.
- [x] Раннер батчей `tmem/corpus_run.py`: сбалансированная очередь (round-robin
      по осям), `manifest.jsonl` (статусы, wall-time, версии), режимы
      `--batches N` / `--all` / `--only` / `--dry-run`, resume по манифесту,
      атомарность батча (перезапуск частично записанного).
- [x] Автогенерация `INTERIM.md` после каждого батча: прогресс, recall по
      стратегиям с накопительными бутстреп-ДИ, срезы тема/персона/lag,
      оценка остатка времени.
- [x] Протокол латентности: warmup (3 холостых хода), ≥5 **чередующихся**
      повторов каждой стратегии (A,B,A,B,…), тайминг end-to-end **включая
      embedding и retrieval** (устраняет занижение латентности RAG-вариантов).
- [x] Чередование порядка стратегий между батчами (снятие дрейфа GPU).
- **Проверка**: юнит-тесты раннера на фейковой стратегии-заглушке (без GPU):
  resume после имитации Ctrl-C между батчами и внутри батча; сбалансированность
  очереди (первые 12 батчей покрывают все темы/ситуации — тест на спецификации
  48 диалогов); `INTERIM.md` создаётся и обновляется. Smoke-прогон выполнен на tiny-модели (CPU, CI-тест
  `tests/test_corpus_smoke.py`); warmup-эффект будет подтверждён на пилоте (GPU).

### Шаг 3. Пилот (spike, таймбокс 1 день GPU)
- [ ] Spec `pilot`: 2 темы × 2 персоны × 3 ситуации × 100 ходов = 12 диалогов
      (латинский квадрат, не полный факториал) × 7 основных стратегий
      (classic_kv_full, streaming, h2o, snapkv, pyramidkv, rag_text_only,
      v4_rag_kv), 1 повтор + 5 повторов латентности. Пилот сам прогоняется
      батчами — сразу обкатывает раннер, манифест и `INTERIM.md` в реальном
      режиме.
- [ ] Замер wall-time **на батч** (диалог × 7 стратегий) для длин 100 и 200
      ходов → календарь GPU-сессий: сколько батчей влезает в окно 2–3 часа.
      Если 200-ходовые диалоги с полным контекстом упираются в 24 ГБ или
      квадратичный prefill — уменьшить ось длины для full-context контроля
      (зафиксировать в отчёте как ограничение).
- **Критерий успеха**: пилот воспроизводит порядки recall из статьи
  (v4_rag_kv > rag_text_only > snapkv/h2o > sliding; full ≈ 1.0) — иначе СТОП,
  разбор причин до масштабирования.

### Шаг 4. Основной прогон — очередь из 48 батчей
- [ ] Grid `main`: 48 диалогов (латинский квадрат 6 тем × 4 персоны ×
      5 ситуаций, 2 длины: 100 и 200 ходов) × 7 стратегий = **48 батчей**,
      каждый запускается и останавливается независимо (`--batches N` на
      сессию GPU). Суммарно ~1–3 GPU-суток, но НЕ подряд — любыми окнами.
- [ ] **Контрольные точки (decision gates)** — заказчик смотрит `INTERIM.md`
      и подтверждает продолжение:
      - ГК-1: после первых 4 батчей — санити-чек (нет NaN/аномалий латентности,
        recall в ожидаемых диапазонах, wall-time совпадает с пилотом);
      - ГК-2: после 16 батчей (≈1/3, покрыты все темы) — первый промежуточный
        срез с ДИ; решение: продолжать as-is / скорректировать оси;
      - ГК-3: после 32 батчей — проверка гипотезы v4 > rag и v4 > pyramidkv на
        текущих данных; решение о доборе оставшихся 16;
      - ГК-4: очередь полна — финальная сводка, переход к шагу 5.
      На любой ГК можно остановиться и держать паузу сколь угодно долго —
      данные предыдущих батчей зафиксированы на диске.
- [ ] Grid `ablation` (отдельная очередь из 16 батчей на подмножестве
      диалогов): `rag_text_only` → `v3_rag_centroid` (+центрирование) →
      +upsert (`rag_crit=0.95`) → `v4_rag_kv` (+латентный канал) и
      `v4_kv_mid` (только латентный); свипы: `kv_slots` {8,16,32,64},
      `rag_k` {2,4,8}, бюджет {64,128,256}. Запускается после ГК-2 основной
      очереди (или параллельными окнами — очереди независимы).
- [ ] Автоотчёт после каждого батча пишется раннером; раз в GPU-сессию —
      беглый контроль манифеста (пропуски, перезапуски, аномалии).
- **Проверка**: `manifest.jsonl` содержит 48 статусов `done` (или явные
  `failed` с причиной), `INTERIM.md` обновлён, сводный JSONL полон
  (сессий = ожидание), каждый диалог имеет все стратегии.

### Шаг 5. Статистика и агрегация — `scripts/aggregate_corpus.py` *(новый)*
- [ ] Статистическое ядро — единый модуль, используемый и раннером
      (`INTERIM.md` после каждого батча, инкрементально по завершённым
      диалогам), и финальной агрегацией: частичные данные всегда считаются
      тем же кодом, что и итоговые.
- [ ] Recall: среднее ± 95 % ДИ (бутстреп по диалогам, не по вопросам —
      вопросы внутри диалога зависимы); срезы: lag-зона × тема × персона ×
      ситуация × тип пробы.
- [ ] Значимость: попарный бутстреп по диалогам для ключевых пар
      (v4_rag_kv vs rag_text_only; vs pyramidkv; vs full) + поправка
      Холма на множественные сравнения.
- [ ] Латентность: медиана и IQR по чередующимся повторам; разложение
      prefill/decode/retrieval; сравнение только по end-to-end.
- [ ] Галлюцинации: доля конкретных ответов на unanswerable-пробы;
      stale-rate на обновлениях; точность temporal-проб.
- [ ] Графики: кривые recall по lag-зонам, heat-map тема×персона, Парето
      recall/attention-прокси с error bars.
- **Проверка**: агрегатор прогнан на синтетическом JSONL-фикстуре с известными
  ответами (тест); числа в графиках == числа в таблице.

## Риски и fallback

| Риск | Митигация |
|---|---|
| Полный факториал 120 диалогов × full-context на 200 ходах = недели GPU | латинский квадрат (48 диалогов); full-context на 200 ходах — только если пилот подтвердит память/время, иначе 100 ходов |
| OOM на 200 ходах (prefill ~0,5М токенов) | чанкованный prefill или cap длины; ось длины — только для компактных стратегий |
| Синтетические диалоги останутся «пластиковыми» | большие пулы filler-ов на тему+персону; опционально (отдельный шаг, вручную верифицируемый) — LLM-генерация реплик с сохранением валидатора уникальности фактов |
| Keyword-скоринг даёт ложные срабатывания на новых темах | валидатор уникальности ключевых строк в spec + ручная выборка 5 % проб с логированием ответа (уже есть в JSON) |
| Латентность всё ещё шумит | чередующиеся повторы + interleaved-порядок стратегий; если CV > 15 % — увеличить повторы до 9 |
| Частичный корпус смещён (остановка на середине охватывает не все темы) | сбалансированная round-robin очередь: любой префикс ≈ равномерно покрывает оси; первые 12 батчей покрывают все темы и ситуации |
| Прогон растянут на недели — дрейф окружения между батчами | манифест фиксирует на батч: git SHA, версию tmem, модель/dtype, GPU; аномалии между окнами видны в `INTERIM.md` (wall-time, латентность full-context как канарейка) |
| Потеря результатов при аварийной остановке внутри батча | атомарность: батч либо завершён и в манифесте, либо перезапускается целиком; потеря — максимум один диалог |

## Оценка трудоёмкости

- Шаг 1–2 (код+тесты, включая раннер батчей и статистику INTERIM): основная
  работа, ~2–3 рабочих дня.
- Шаг 3 (пилот): 1 день GPU (таймбокс; **spike first** — точная оценка
  появится только после замера).
- Шаг 4: ~1–3 GPU-суток суммарно, разбитые на независимые окна (батчи).
- Шаг 5–6: ~1 рабочий день.

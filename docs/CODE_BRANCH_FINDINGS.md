# Код-ветка (codemem): архитектура + первые эмпирические находки

Отдельная система (`codemem/`, `scripts_code/`, `tests_code/`, `results/code/`),
не переиспользует диалоговый `tmem`. Общая идея: центрирование + статическое
хранение + динамический выбор. Архитектура из `для кода.md` + уточнения по рискам.

## Архитектура (реализована, фазы 0–4)
- **Цель из запроса** → генерация → сжатие (метрика верности cos(full,compressed);
  на smoke 0.884) → эмбеддинг mid full-attn слоя (15, [N,2560]).
- **Дерево целей**: рекурсивная бинарная декомпозиция (дендрограмма average-linkage,
  root-gap ≥ tau_split + бинарный судья «оба подцеля самодостаточны?»), depth cap 2.
- **Двухуровневый запрос**: цель маршрутизирует поддерево (грубо), потребность =
  центрированный residual-запрос внутри (мелко).
- **Статический банк чанков**: ключи не мутируют; tiers зрелости WRITTEN→USED→VERIFIED
  (retroactive promotion, без execution-гейта на записи — инкрементальная кодовая
  база); use-скор по успешному применению.
- **Живой компонент = предсказания (prefetch, TTL по шагу плана) + use-скоры**,
  не мутирующие векторы. Prefetch — источник кандидатов, не привилегированная
  секция: единый MMR-ранкинг (anchoring убран конструктивно).
- **Write-back**: сходство с целью ≥ tau → ассимиляция в узел, иначе новая
  решённая подцель. Chunked-генерация с план-шагом WANT/NEED.
- 32 offline-теста (tests_code/), smoke端到end на GPU работает (2 чанка, 25s).

## Retrieval-абляция (taskq, r2): разложение механизмов
Корпус 79 функций, 45 запросов (15 задач × 3 парифразы), слой 15, k=6.
8 условий, разнесены центрирование ⊥ диверсификация ⊥ routing. Bootstrap 95% CI
по запросам, paired-контрасты (ниже = лучше, None = промах).

| условие | hit@6 [95% CI] | MRR |
|---|---|---|
| flat_plain | 0.733 [0.60, 0.84] | 0.652 |
| flat_diverse (MMR) | 0.733 [0.60, 0.84] | 0.649 |
| flat_centered | 0.644 [0.49, 0.78] | 0.611 |
| flat_centered_diverse | 0.644 [0.49, 0.78] | 0.596 |
| **goal_uncentered** | **0.867 [0.76, 0.96]** | 0.754 |
| goal_centered | 0.800 [0.67, 0.91] | 0.753 |
| goal_prefetch | 0.800 [0.67, 0.91] | 0.753 |
| needroute (по потребности) | 0.267 [0.13, 0.40] | 0.267 |

Paired (treatment vs baseline): +better/−worse/=equal
- routing (goal_centered vs flat_centered_diverse): **+9/−0/=36** — робастно, never-worse.
- centering_flat (flat_centered vs flat_plain): +7/−8/=30 — net отрицательно.
- centering_goal (goal_centered vs goal_uncentered): +4/−3/=38 — шум.
- diversification_flat (MMR vs plain): +1/−1/=43 — шум.
- prefetch (goal_prefetch vs goal_centered): +0/−0/=45 — идентично, never-worse.
- oracle_vs_needroute: +0/−24/=21 — routing по потребности катастрофичен.

## Находки (честно, с контрастом к диалоговой ветке)
1. **Goal routing — load-bearing для кода.** Ограничение поиска правильным
   поддеревом убирает cross-goal дистракторы: hit@6 0.644→0.80/0.87, +9/−0
   (знаковый тест p≈0.002). Это two-stage выгода (CLAG/IVF/RAPTOR).
2. **Центрирование НЕ помогает на этой code-задаче** — на flat net отрицательно
   (+7/−8), внутри goal шум (+4/−3, uncentered даже чуть лучше). **КОНТРАСТ с
   диалогом**, где центрирование было load-bearing (+0.041 recall). Выгода
   центрирования задачно-зависима и не переносится на code retrieval с
   docstring-подобными потребностями. Глобальный центроид разнородного корпуса
   вычитает полезный сигнал; локальный (в goal-узле) — нейтрален.
3. **MMR-диверсификация ≈ нет эффекта на flat** (+1/−1). Clone-flooding выгода из
   диалога здесь не проявилась: utils.retry по-прежнему погребён клонами
   (backoff_delay/clamp) во ВСЕХ условиях — MMR lam=0.5 его не достаёт.
4. **Prefetch добавляет 0** (идентично, never-worse) — согласуется с уроком
   memctx≡диверсификация. Каскад работает конструктивно, но выгоды здесь нет.
5. **Routing ДОЛЖЕН использовать цель, не потребность.** needroute +0/−24:
   локальная потребность слишком специфична для выбора поддерева; цель даёт
   правильный грубый контекст. Это валидирует двухуровневый дизайн (цель
   маршрутизирует, потребность ищет внутри) — routing по потребности коллапсирует.

## Оговорки (мощность/валидность)
- **Routing — oracle-goal-conditioned** для goal_centered (даём правильную цель +
  функции вручную сгруппированы по модулям). Это ВЕРХНЯЯ граница выгоды routing;
  практическая выгода зависит от качества оценки цели и семантической группировки
  (write-back). needroute показывает хрупкость при неверном сигнале routing.
- Парифразы коррелированы внутри задачи → bootstrap по запросам слегка завышает
  мощность (кластеризация по задачам не учтена). Routing +9/−0 робастен независимо.
- Один слой (15), один корпус (taskq)..Layer-зависимость и перенос на другие
  корпуса не проверены. Центрирование-негатив может быть layer/query-специфичен.
- n=15 задач (45 запросов) — мало для публикации; нужны повторы/корпуса/ДИ.

## Статус
Фазы 0–4 реализованы, 32 offline-теста + smoke + абляция зелёные. Коммиты по фазам.
Главный научный итог: **для code retrieval load-bearing — goal routing, а не
центрирование/диверсификация** (контраст с диалогом). Честное эмпирическое
разложение + негативные результаты по переносу механизмов — вклад в нашей рамке.
